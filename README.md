# Titanic Inference Strategies and Model Serving with FastAPI

## Project overview
This assignment trains one classification pipeline on Kaggle's Titanic `train.csv`, evaluates it on a held-out test split, saves the full preprocessing/model pipeline as `model.pkl`, and reuses that same artifact for online, batch, streaming, and REST API inference.

Dataset: https://www.kaggle.com/competitions/titanic/data

## Setup
Use Python 3.10 or newer.

1. Download **train.csv** from the Kaggle dataset link above.
2. Put it at `data/train.csv` (do not rename the columns).
3. Create and activate a virtual environment if desired.
4. Install dependencies:
   ```bash
   python -m pip install -r requirements.txt
   ```

## Run all assignment tasks in order
```bash
python train_model.py
python online_inference.py
python batch_inference.py
python streaming_inference.py
```

`train_model.py` prints the measured held-out accuracy and writes `reports/evaluation.txt`. The exact score is calculated from the dataset and installed library versions when you run it; do not copy an unmeasured accuracy into the report. It saves the complete preprocessing + logistic-regression pipeline to `model.pkl`.

The inference scripts use records from the deterministic 20% held-out portion of `train.csv`. These records were not used to fit the model. Their `Survived` labels are not passed to the inference calls.

## Start and test the API
Start the server in one terminal:
```bash
uvicorn app:app --reload
```
Open:
- Health: http://127.0.0.1:8000/health
- Swagger UI: http://127.0.0.1:8000/docs

In Swagger UI, test `GET /health`, then `POST /predict` with this valid JSON:
```json
{
  "Pclass": 3,
  "Sex": "male",
  "Age": 22,
  "SibSp": 1,
  "Parch": 0,
  "Fare": 7.25,
  "Embarked": "S"
}
```
Test validation with an invalid request, for example `Pclass: 9`, or `Sex: "unknown"`. Pydantic should return HTTP 422 Unprocessable Entity. With `extra="forbid"`, unexpected fields are also rejected.

In a second terminal:
```bash
python client.py
```

## Observations
1. **Online vs batch:** Online inference predicts one record per request and is suited to low-latency individual predictions. Batch inference predicts many records in one call and is efficient for bulk processing.
2. **Streaming vs batch:** Streaming processes records as they arrive, here one record every second. Batch collects a group of records and processes the group together.
3. **Why FastAPI:** It provides typed request validation through Pydantic, automatic interactive Swagger documentation, and straightforward HTTP endpoints for model predictions.
4. **Why reuse one model:** It keeps predictions consistent across inference modes and avoids differences caused by retraining, preprocessing drift, or different model versions.
